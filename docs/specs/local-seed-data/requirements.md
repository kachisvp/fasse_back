# requirements.md — 開発用 DB へのテストデータ投入

## 背景

- 開発用 DB(`fasse`)はテーブルのみが作成された空の状態で始まるため、ローカル起動後に画面や API を試すには、マスタから順に手作業でデータを登録する必要がある
- 自動テスト用のテストデータ(`src/test/resources/testdata/<テーブル名>.csv`)は、マスタ・消費税率・伝票を業務として自然な内容で揃えており、開発時の確認用データとしてもそのまま使える
- テストデータの投入処理(`TestDataLoader`)は、誤って開発データを消さないよう `_test` で終わるデータベースにしか投入できない

## 目的

コマンド 1 つで、開発用 DB(`fasse`)にテストデータを投入できるようにする。

## スコープ

- Gradle タスク `seedLocal` による、`local` プロファイルの接続先 DB へのテストデータ投入
- 投入するデータは `src/test/resources/testdata/` の CSV をそのまま使う(シード専用のデータは作らない)

## ユーザーストーリー

- 開発者として、ローカル環境を構築した直後に、画面や API をすぐに試せるデータを入れたい
- 開発者として、動作確認でデータが崩れたときに、いつでも同じ状態に戻したい

## 受け入れ基準

### 機能

- [ ] `gradlew.bat seedLocal -Pconfirm=yes` で、`application-local.yaml` の接続先 DB に `testdata/` の全 CSV が投入される
- [ ] 投入前に対象テーブル(`docs/specs/purchase-sales/design.md` 10.2 節の 9 テーブル)のデータがすべて削除される。`flyway_schema_history` は変更しない
- [ ] テーブルが未作成の場合は、投入前に Flyway のマイグレーションを適用する(アプリケーションを一度も起動していなくても実行できる)
- [ ] 削除と投入は 1 トランザクションで行い、途中で失敗した場合は実行前のデータに戻る
- [ ] 投入後にアプリケーションから伝票を登録しても、伝票番号がテストデータと重複しない
- [ ] 投入後にアプリケーションからマスタを登録しても、id がテストデータと重複しない

### 安全性

- [ ] `-Pconfirm=yes` を指定しない場合は、DB に接続せずに終了し、全件削除される旨と指定方法を表示する
- [ ] 接続先のホストが `localhost` / `127.0.0.1` / `::1` 以外の場合は、データを変更せずにエラー終了する(stg 等への誤投入を防ぐ)
- [ ] 自動テスト用の `TestDataLoader` は、引き続き `_test` で終わるデータベースにしか投入できない
- [ ] DB のパスワード等の接続情報をログに出力しない

### テスト・品質

- [ ] 実行可否の判定(`confirm` の指定、接続先ホスト)に単体テストがある
- [ ] 既存のテストがすべて成功し、`gradlew.bat build` が成功する

## スコープ外

- シード専用データの作成・管理(テストデータと分けて管理する必要が生じた時点で別途検討する)
- stg / dev(AWS)環境へのデータ投入
- 既存データを残したままの追加投入(差分投入)
